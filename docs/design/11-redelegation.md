# 11. 재위임 — 작업 중 다른 팀에 하위 요청 만들기 (CLO-20)

> 상태: **확정(2026-09-28)** — §6 세 항목 모두 제안대로 결정.

## 1. 문제

A 팀이 B 팀에 요청을 보냈다. B 가 작업하다 보니 C 팀(다른 전문가)의 도움이 필요하다.
지금은 B 가 C 에게 **맨바닥부터 새 요청**을 써야 한다. 원본 요청의 지시·첨부·지금까지의 결과를 손으로 옮겨야 하고,
두 요청이 서로 이어져 있다는 기록도 남지 않는다.

## 3. 제안

### 3-1. 모델

- `Request.parentRequestId`(nullable, 자기 참조) + `parentRevisionNo`(재위임 시점의 부모 차수).
- 하위 요청은 **보통 요청과 똑같다**: 보내는 팀 = B, 받는 팀 = C. 수락·실행·결과 검토·완료 흐름도 동일하다.
  → 사람 승인 원칙 유지(C 가 수락해야 실행, B 가 결과를 승인해야 완료).
- 경로 권한은 기존 validateRoute 를 그대로 쓴다(B→C TeamLink 필요).

### 3-2. 언제 만들 수 있나

- 부모가 B 에게서 **진행 중**일 때: ACCEPTED · READY_TO_RUN · RUNNING · RESULT_REVIEW.
- 부모의 **받는 팀 구성원**만(= B). 하위 요청 하나의 깊이 제한은 두지 않되 순환(자기 조상에게 다시 보내기)은 막는다.

### 3-3. 맥락 상속 (하위 요청 1차수에 자동으로 들어가는 것)

- 부모 원본 지시(현재 차수) — 읽기 전용 "원본 요청" 블록으로.
- 부모 첨부(문서 버전·파일) — B 가 체크박스로 고른 것만(기본 전부). C 가 볼 수 있게 권한을 부여.
- 부모의 지금까지 결과 요약 — B 가 승인한 결과만(검토 전 결과는 B 가 선택 시).
- B 가 쓰는 "C 에게 부탁할 것" 지시.

### 3-4. 끝난 뒤

- 하위 요청이 COMPLETED 되면 부모 타임라인에 `request.child_completed` 가 남고, 부모 상세에 결과 요약 링크가 뜬다.
- 부모를 다음에 실행할 때 에이전트 맥락(`previousWork`)에 **완료된 하위 요청 결과 요약**을 넣는다.
- 하위 요청이 진행 중이어도 부모는 막지 않는다(표시만).

### 3-5. 화면·타임라인

- 부모 상세: "다른 팀에 도움 요청" 버튼 → 재위임 폼(받는 팀·담당자·지시·상속할 첨부 선택). "하위 요청" 섹션(팀·상태·결과).
- 하위 상세: 상단에 "○○ 요청에서 이어짐" 링크와 원본 요청 블록.
- 타임라인: 부모 `request.delegated`, 하위 `request.created`(payload 에 parent), 부모 `request.child_completed`.

## 4. 범위 밖(다음 단계)

- 에이전트가 스스로 재위임을 **제안**(MCP 도구 → 하위 요청 초안 DRAFT 생성, B 가 확인 후 보냄).
- 하위 요청 결과를 부모 결과에 자동 병합.

## 5. 작업 순서(승인 후)

1. 마이그레이션 + shared DTO/타임라인 이벤트 + 서버 서비스·권한·테스트 (codex 구현, 테스트는 다른 세션)
2. 웹: 재위임 폼, 부모·하위 상세 표시
3. 실행 맥락에 하위 결과 포함
4. dev 배포 후 계정 2~3개로 실제 흐름 확인

## 6. 결정 (2026-09-28 사용자 확정)

1. 원본 요청자(A)에게 하위 요청을 보여줄지 — → **존재와 상태만**(내용은 B·C 만).
2. 1단계는 사람이 웹에서만 재위임, 에이전트 제안은 다음 단계 → 그렇게 한다.
3. 부모 첨부를 C 에게 공유할 때 기본값 → 전부 체크(B 가 해제 가능).

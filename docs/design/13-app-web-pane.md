# 13. Mac 앱에서 웹 동작 쓰기 — 1단계: 요청 화면을 앱 창에 넣기

> 상태: **확정(2026-09-30)**. CLO-21(워크플로 템플릿) 등 확장 기능보다 앱 편의를 먼저 한다는 사용자 결정.

## 1. 문제

Baton 앱에는 설정·활동 기록만 있다. 요청 확인·수락·결과 승인·새 요청은 브라우저에서 웹을 열어야 한다.
알림을 눌러도 브라우저로 튕겨 나간다. 다른 상단바 앱(Slack·Linear 등)은 앱 안에서 다 된다.

## 2. 결정

- **1단계(이 문서)**: 앱 창에 "요청" 항목을 추가하고 그 안에 Baton 웹 화면을 띄운다(WKWebView).
  웹의 모든 동작을 바로 쓸 수 있고, 웹을 고치면 앱에도 그대로 반영된다.
- **2단계**: 상단바 창에서 자주 쓰는 동작을 네이티브로.
  - 2-A(완료 9c37d90): "내 차례" 목록·아이콘 옆 건수, 조회만(기기 토큰, `GET /v1/desktop/inbox`).
  - 2-B(**하지 않음**, 2026-10-06 사용자 결정): 상단바에서 바로 수락·결과 승인. 내용을 읽지 않고 상태를 바꾸게 되어 위험하다.
    상태를 바꾸는 동작은 앱 창(요청 화면)에서 요청 내용을 본 뒤에 한다.
- 모든 화면의 네이티브 재구현은 하지 않는다(요청 상세만 웹 1,300줄 — 기능마다 두 번 만들게 된다).

## 3. 1단계 설계

- 사용자 API 는 사용자 로그인 토큰(JWT)이 필요하다. 기기 토큰으로는 안 된다(`apps/server/src/auth/auth.service.ts` current()).
  → 앱 안 웹 화면에서 accounts 로그인을 **한 번** 한다. 토큰은 WKWebView 기본(영구) 저장소의 localStorage 에 남아 재실행 후에도 유지.
- 창: 사이드바 첫 항목 "요청"(기본 항목). 뒤로·앞으로·새로고침·브라우저에서 열기, ⌘R·⌘[·⌘].
- 머무는 곳: Baton 서버 주소와 **로그인 경로(accounts)** 는 창 안에서, 그 밖의 링크는 기본 브라우저로.
- 파일: 첨부 올리기(`<input type=file>`) 열기 창, 내려받기는 ~/Downloads(같은 이름이면 번호 붙임) 후 Finder 에서 보이기.
- 웹의 확인 창(confirm/alert/prompt)은 네이티브 대화상자로.
- 알림 클릭·상단바 "최근 알림" 클릭: 주소가 Baton 서버면 **앱 창의 그 요청**을, 아니면 브라우저를 연다.
- 상단바 창에 "요청 열기" 버튼.
- 서버 주소를 바꿔 저장하면 새 주소로 다시 읽는다. 서버 주소가 없으면(페어링 전) 안내 문구.

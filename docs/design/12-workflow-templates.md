# 12. 워크플로 템플릿 — 여러 팀을 정해진 순서로 거치는 요청 (CLO-21)

> 상태: **보류(2026-09-30)** — 사용자 결정: 확장 기능보다 기본 기능·앱 편의를 먼저. 다시 꺼낼 때 §6 결정부터.

## 1. 문제

장애 대응·릴리스 점검처럼 반복되는 업무는 늘 같은 팀들을 같은 순서로 거친다(예: 운영팀 → 백엔드팀 → QA팀).
지금은 단계마다 요청을 새로 쓰고, 앞 단계 결과를 손으로 옮기고, 다음이 누구 차례인지 사람이 기억해야 한다.

## 2. 지금 구조에서 쓸 수 있는 것 (main @ c95e4b6)

| 항목 | 현재 |
|---|---|
| 요청 | 보내는 팀 → 받는 팀 1:1, 경로 권한은 TeamLink(보내는 팀→받는 팀) |
| 완료 | 받는 팀 결과를 보낸 쪽이 승인하면 COMPLETED |
| 요청 사이 연결 | CLO-20 재위임의 `parentRequestId`(부모·자식) — 순서 있는 단계 연결은 없음 |
| 정책(policy) | 요청이 아니라 **실행 준비** 단계에서 받는 쪽이 정한다(위험 승인·git 쓰기 정책, 설계 07·09) |

## 3. 제안

### 3-1. 모델

- `WorkflowTemplate`: 조직·소유 팀, 이름, 설명, 단계 목록.
- `WorkflowTemplateStep`: 순서, 받는 팀, 담당자(선택), 제목 틀, 기본 지시, 기본 첨부(선택).
- `WorkflowRun`: 템플릿으로 시작한 한 번의 진행. 시작 시점의 단계 목록 **스냅샷**(템플릿이 나중에 바뀌어도 진행 중인 건은 그대로), 시작한 사람·팀, 현재 단계, 상태(진행 중·완료·중단).
- `Request.workflowRunId` + `workflowStepNo`: 각 단계는 **보통 요청**이다(수락·실행·결과 승인 흐름 동일, 사람 승인 원칙 유지).

### 3-2. 흐름 (제안: "시작한 사람이 순서대로 보낸다")

1. 템플릿에서 **시작** → 1단계 요청 작성 화면이 틀로 채워져 열린다(내용 수정 가능) → 보낸다.
2. 1단계 결과를 시작한 사람이 승인해 COMPLETED 가 되면, 요청 상세와 목록에 **"다음 단계: ○○팀에 보내기"** 제안이 뜬다.
   작성 화면은 2단계 틀 + **앞 단계 승인 결과 요약**으로 채워진다. 사람이 확인하고 보낸다(자동 전송 없음).
3. 마지막 단계가 끝나면 WorkflowRun 완료. 중간에 "중단"할 수 있다.

- 모든 단계의 보내는 팀 = 시작한 사람의 팀 → 경로 권한은 기존 TeamLink 그대로(시작 팀 → 각 단계 팀). 템플릿 저장 시 링크가 없는 단계는 경고.
- 한 번에 한 단계씩만 진행(병렬 단계는 범위 밖).

### 3-3. 화면

- **템플릿 관리** `/templates`: 목록·만들기·수정·삭제(보관). 단계 추가·순서 바꾸기·팀 선택·기본 지시.
- **새 요청** 화면에 "템플릿에서 시작" 선택.
- **요청 상세**: 워크플로 단계 표시(1/3 · 운영팀 → **백엔드팀** → QA팀), 완료 후 "다음 단계 보내기" 버튼.
- **진행 목록**: 내 워크플로 진행 현황(현재 단계·상태). 1단계는 요청 목록 배지 "워크플로 2/3" 로 대신해도 된다.

### 3-4. 에이전트 맥락

- 2단계 이후 요청을 실행할 때 에이전트에게 "이 요청은 ○○ 워크플로의 2/3 단계, 앞 단계 결과 요약: …" 을 넘긴다
  (재위임의 상위 요청 맥락과 같은 방식).

## 4. 범위 밖(다음 단계)

- 단계별 **정책 기본값**(위험 승인·git 쓰기) — 정책은 실행 준비에서 받는 쪽이 정하는 구조라, 템플릿 값은 "권장값 표시" 로 따로 설계.
- 병렬 단계·조건 분기, 앞 단계 팀이 직접 다음 단계로 넘기는 릴레이 방식(§6-1 의 다른 안).

## 5. 작업 순서(승인 후)

1. 스키마·마이그레이션 + 템플릿 CRUD API + 워크플로 시작/다음 단계 API + 테스트 (codex 작성, 리드 검증)
2. 웹: 템플릿 관리, 템플릿에서 시작, 요청 상세 단계 표시·다음 단계 보내기
3. 실행 맥락에 워크플로 단계·앞 단계 결과
4. dev 배포 후 확인

## 6. 사용자 결정 필요

1. **다음 단계는 누가 보내나** — 제안: **시작한 사람**(각 단계 결과를 시작한 사람이 승인하고 다음 단계를 보냄).
   다른 안: 앞 단계를 맡은 팀이 이어서 넘기는 릴레이(단계 팀끼리 TeamLink 필요, 시작한 사람은 지켜보기만).
2. **템플릿은 누구 것인가** — 제안: **팀 템플릿**(그 팀 구성원이 만들고 쓰고 고친다. 조직 관리자는 전부 관리).
3. **단계별 정책 기본값** — 제안: 이번에는 빼고 다음 단계로.
